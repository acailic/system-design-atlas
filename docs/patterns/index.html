Patterns index: design lessons that recur

The deep-dives teach systems; this index teaches design. Each pattern appears in two or more canonical codebases — the recurrence is the signal.

The deep-dives teach systems; this index teaches design. Each pattern below appears independently in two or more canonical codebases — usually invented by one and rediscovered (or inherited) by the others. That recurrence is the strongest signal in the atlas: when very different teams under different constraints converge on the same shape, you are looking at a real pattern, not a fashion.

Read this file two ways: top-down as a course in applied system design (each pattern ends with "reach for it when…"), or bottom-up as a back-of-the-book index into the deep-dives.

1. Content addressing (name things by their hash)

Shape: immutable artifacts whose identifier is a digest of their bytes; identity, integrity, and dedup collapse into one mechanism.

Seen in: git — the entire object database is hash-keyed, so verification and dedup are free; Moby — image layers are digest-named, which is why registries are dumb blob stores and builds cache globally.

Why it recurs: it deletes an entire class of coordination problems (no registry to maintain, no trust needed in transport), and it makes caching trivially correct.

Reach for it when: artifacts are immutable or versioned, produced once and consumed many times. Beware: it converts "update" into "add new + garbage-collect old" — you are signing up for a GC story.

2. Write-ahead logging (make the log the truth)

Shape: append the change to a log before (or instead of) mutating data pages; recovery = replay; durability = fsync the log.

Seen in: SQLite — journal and WAL as selectable modes behind the pager; PostgreSQL — XLogInsert/redo as the durability mechanism for every subsystem; LevelDB — WAL as the boundary between "durable" and "cache"; Kafka — where the log stops being a technique and becomes the product; etcd — raft entries and snapshots framed in a WAL the server replays on restart; Elasticsearch — the translog is the WAL that decouples "searchable" (refresh) from "durable" (flush); ZooKeeper — FileTxnLog appends every proposal and fsyncs before the follower acks, so election is just "highest log wins"; RocksDB — one WAL multiplexed over column families whose CF-tagged record types double as a prepare/commit/rollback transaction protocol; Prometheus — the TSDB head's WAL protects only recent samples and fsyncs at segment rotation, a deliberately lighter durability point because metrics are re-scrapeable; TiDB — TiKV's raft-engine is the log: consensus entries persist there while applied state goes to RocksDB, whose own WAL the apply path can skip because the Raft log replays anything un-applied (raftstore fsm/apply.rs).

Why it recurs: sequential appends are the cheapest thing storage does; a single log turns unbounded crash-consistency problems into one mechanical replay.

Reach for it when: you must survive crashes — which is always. The pattern's costs are write amplification and a checkpoint/compaction story, both cheaper than the alternative.

3. Immutable core, tiny mutable surface

Shape: the bulk of state is append-only/immutable; all mutation is concentrated in one small, carefully synchronized component.

Seen in: git — objects never change; refs are the only mutable pointers; LevelDB — SSTables are immutable; the manifest (itself a log) is the mutable layout; Kafka — KRaft moved broker metadata into an append-only raft log; Prometheus — the mutable surface is the head block (WAL-backed memory + m-mapped chunks); history lives in immutable time-windowed blocks that compaction merges upward and retention deletes whole.

Why it recurs: small mutable surfaces are auditable, lockable, and crash-safe; everything else becomes shareable and cacheable.

Reach for it when: reads dominate writes and history matters. The price is always a GC/compaction subsystem — budget it from day one.

4. Supervisor + expendable workers

Shape: a stateless supervisor owns listening sockets/lifecycle; per-connection or per-job work happens in workers whose death is an incident, not an outage.

Seen in: nginx — master holds the sockets, workers die and respawn; PostgreSQL — the postmaster forks backends, one connection per process; Redis — persistence by fork: the child is an expendable snapshotter over copy-on-write memory; Apache httpd — the MPM parent supervises score- board-tracked children and respawns them while a graceful restart drains the old generation; Servo — the constellation thread supervises expendable pipelines (script threads or sandboxed child processes) and is chaos-tested against random pipeline death; HAProxy — the master re-executes itself per reload and the old worker hands its listening sockets to the new one over a socketpair, so the supervisor ever only owns supervision, never a single connection; Chromium — the browser process supervises sandboxed renderer processes it assumes are hostile: a dead renderer is a sad tab and a policy-ladder respawn, and a lying one is killed on a catalogued BadMessageReason.

Why it recurs: crash containment composes; supervision is easy precisely when the supervisor owns nothing user-visible.

Reach for it when: work is parallelizable and per-unit state is small. Workers that hold large in-memory state (databases' backends mid-transaction) pay on restart — that's the trade PostgreSQL accepts knowingly.

5. Event loop / readiness demultiplexing

Shape: one thread per process blocks in epoll/kqueue and dispatches callbacks; concurrency without shared-memory parallelism.

Seen in: Redis — ae loop, plus the evolution of IO threads around a still-serial command core; nginx — one loop per worker with state machines instead of threads; Memcached — one libevent loop per worker thread, connections dispatched round-robin at accept; libuv — the pattern distilled into a portable library: phases, watcher queues, and a poller backend per OS; Envoy — one dispatcher per worker thread over thread-local config snapshots; curl — the tenant's side of the same contract: a transfer state machine that rents any foreign loop via pollsets; Servo — one task-queue event loop per site-instance script thread implements the WHATWG event-loop processing model, so one page's hang cannot stall another site; HAProxy — one poll loop per thread, but with the loop's own scheduler made explicit: budgeted tasklet run queues in ebtrees, weighted by class, policed by a CPU-time watchdog; Go runtime — the readiness demultiplexer hidden under a thread scheduler: epoll parks and readies whole goroutines, so the loop exists but user code never sees a callback; Chromium — every process is threads-over-queues: the browser's named UI/IO threads plus a trait-tagged ThreadPool, and renderers whose main thread is the HTML event loop — with PostTask messages, not locks, as the officially documented cross-thread contract.

Why it recurs: I/O-bound servers are bounded by ready descriptors, not by CPU; a loop removes per-connection stacks and most locking.

Reach for it when: workload is I/O-bound with cheap per-event work. The moment per-event work is CPU-heavy you need the worker/ process variants (pattern 4) or threads — C10K logic does not survive a 100ms handler.

6. Amortize every unbounded operation

Shape: rehash, expiry, compaction, and freeing move a bounded amount of work per operation or per tick, never in one burst.

Seen in: Redis — incremental rehash and time-budgeted active expiry; LevelDB — leveled compaction with slowdown/stop triggers; PostgreSQL — vacuum as a background GC with autovacuum tuning; Kubernetes — resync periods as a safety net under the event stream; Memcached — hash-table expansion by a background thread moving buckets under the same stripe locks the request path uses; Lua — the GC advances in allocation-debt-paced steps (luaC_step) so a guest language never pauses its host's frame budget; linux — kswapd reclaims memory in budgeted background passes so allocation never stalls on a full scan, and readahead turns one small read into a window of prefetched I/O so the next reads hit the page cache; Go runtime — the whole GC is this rule at war with an allocation rate: concurrent mark on a 25% CPU budget, allocation billed as scanning debt (gcAssistAlloc), and Green Tea batching spans to keep each unit of mark work cache-local; RocksDB — compaction budgets made explicit: a token-bucket rate limiter throttles background I/O while a stall ladder turns overload into published, steerable slowdown states; V8 — marking runs as allocation-paced steps on the main thread plus concurrent jobs on the embedder's platform, with the store-path write barrier as the mutator's tax that buys never stopping for one big collection (ConcurrentMarking::RunMajor, IncrementalMarking::AdvanceOnAllocation); ClickHouse — background k-way merges keep the part tree shallow while inserts seal new parts, and the Aggregator flips to two-level tables at a size threshold so the final merge parallelizes; HotSpot — the whole tiering idea is amortized optimization (compile only what the counters say is hot), and G1 shrinks each pause by evacuating only a region collection set sized against a declared pause goal (G1YoungCollector::collect, the MaxGCPauseMillis MMU tracker in G1Policy), while ZGC moves marking and relocation off the mutator entirely — the pauses left are two sub-millisecond stack scans; Prometheus — full head chunks m-mapped off the heap by a background loop, head ranges frozen into blocks by a budget-watching compactor that warns when it falls behind, and the WAL truncated by checkpointing.

Why it recurs: latency SLOs are p99 problems; any O(n) pause inside a request path eventually lands in someone's tail.

Reach for it when: anything grows. The rule of thumb from these codebases: if the work is unbounded, it belongs to a background loop with a budget, not to the request.

7. Declarative state + reconcile loops

Shape: clients write desired state; controllers observe and converge; events are hints, truth is compared, not remembered.

Seen in: Kubernetes — the entire control plane; Moby — Config/HostConfig/State is the same spec/status split at container granularity (and restart policies are a reconcile loop over exit states); NATS — JetStream converges stream placement toward desiredRaftGroup state when servers fail or are added; Prometheus — rule groups re-derive complete state every evaluation: alert rules reconcile the active-alert map against the current query result, stale-mark series the previous eval produced, and even restore their for timers after a restart by querying the ALERTS_FOR_STATE series they wrote to their own TSDB.

Why it recurs: distributed systems miss events; idempotent convergence from any state survives what edge-triggered designs cannot.

Reach for it when: multiple unreliable actors must eventually agree on a world state. Cost: everything becomes eventually consistent, and debugging means diffing desired vs actual.

8. Quarantine the environment behind one interface

Shape: all OS/platform dependency funnels through a narrow abstraction; ports are implementations of it.

Seen in: SQLite — VFS is why it runs from phones to airliners; LevelDB — Env as the whole OS surface; nginx — event-module vtables (epoll/kqueue/select behind one macro); libuv — the whole product is this pattern: one loop core, one uv__io_poll per platform; RocksDB — Env later split into FileSystem

  • SystemClock when the single OS seam itself grew too broad.

Why it recurs: portability is architectural, not a build flag; the interface is where testing doubles (in-memory VFS, memdb) come from.

Reach for it when: the system must outlive your current platform assumptions. The failure mode is a leaky abstraction — SQLite's VFS survived because its contract stayed small and honest.

9. Versioned data for concurrent readers (MVCC)

Shape: writers create new versions; readers pick a snapshot; "current" is a query, not a location.

Seen in: PostgreSQL — xmin/xmax and snapshots from the procarray; Kubernetes — resourceVersion optimistic concurrency over every object; LevelDB — compaction drops versions below the oldest live snapshot; etcd — the whole keyspace is revision-stamped history, watch replays it, compaction truncates it; linux — RCU is the same bet at memory granularity: readers walk page-cache and dentry structures under rcu_read_lock with no locks at all, writers publish replacements atomically, and reclamation waits a grace period (synchronize_rcu); TiDB — MVCC pushed out of the database engine entirely: one global clock (PD's TSO) stamps versions, TiKV stores them as key+timestamp records in two column families with in-flight intents in a third (Percolator's layout), and readers resolve "latest version ≤ my snapshot" with a seek.

Why it recurs: locking readers against writers is the bottleneck MVCC deletes; every system that did it never went back.

Reach for it when: read concurrency matters more than write amplification. Always pair it with a GC story (vacuum, compaction).

10. Extension seams placed where the design flexes

Shape: third parties extend the system without forking it, through hooks located at genuine joints (planner, filters, drivers, process boundaries).

Seen in: PostgreSQL — planner/ executor hooks spawned Citus and TimescaleDB; nginx — phase handlers and filter chains; SQLite — VFS, virtual tables, loadable extensions; Kubernetes — CRDs turn the API server into a platform; CPython — the C API whose safety shaped (and constrained) everything, including the GIL; Moby — plugin protocols and OCI-standardized boundaries; VS Code — the stable/proposed two-tier API plus LSP/DAP as protocol-level seams; Apache httpd — hooks, filters, and even the process model (MPM) are extension surfaces, which is why one binary served a decade of web-ecosystem roles; Envoy — network/HTTP filter factories plus registered load-balancer policies make even core scheduling an extension; curl — connection filters and protocol scheme tables as composable seams; llama.cpp — model architectures as graph-builder files (160 of them) over a dumb tensor core; Lua — the metatable protocol as the single seam users build inheritance, prototypes, and DSLs through; Node.js — two deliberate tiers: a private internalBinding seam that churns with V8 and a frozen N-API C ABI that lets precompiled native addons outlive engine upgrades; FFmpeg — codecs, demuxers, muxers, and filters as plain C structs behind one callback contract each (with per-arch SIMD as a second dispatch seam), which is how 880 compatible implementations coexist in one program; PyTorch — every extension (custom ops, backends, interceptors, compilers) registers at the one dispatch table, which is how eager Python stayed a platform; Caddy — every extension point is a namespace-addressed slot in one typed JSON config, resolved by reflection at provisioning time, which is how 133 modules compose behind one static binary; Servo — the engine grew an embedding API (ServoBuilder/WebView delegates, protocol registry, factory traits) so shells and C hosts (servoshell, ffi/capi) extend without forking; linux — vtables at every layer joint (file_operations, sched_class) let thousands of filesystems and drivers — and, via sched_ext, even whole CPU scheduling policies as BPF programs — extend a monolith without forking it; Neovim — msgpack-RPC as the one seam for UIs, embedders, plugin hosts, and even the built-in terminal UI (a child process speaking the same protocol), with additive-only versioning making it safe for a decade of clients; LLVM — passes as the plugin unit: one C symbol (llvmGetPassPluginInfo) registers pipeline-parsing callbacks into the PassBuilder, so out-of-tree optimizers (Enzyme's autodiff) hook the compiler without forking it — and the pass registry itself is the seam the -passes pipeline language plugs into; HotSpot — garbage collection as the pluggable room: five collectors (Serial, Parallel, G1, ZGC, Shenandoah) behind one CollectedHeap + BarrierSet contract, each also emitting its barriers per compiler and per architecture (gc/g1/c1, gc/g1/c2, cpu/x86/gc/z/z_x86_64.ad), selected by a startup factory (GCConfig::select_gc); TiDB — the kvproto service contract plus PD placement rules are the seam: a columnar engine (TiFlash) joined the system as just another Raft replica of the same regions, with the SQL layer unchanged.

Why it recurs: ecosystems compound only where extension is contractual; the seams' placement decides which ecosystem you get.

Reach for it when: you can name who will extend you and what they will want to change. Misplaced hooks become load-bearing mistakes (CPython's is both its greatest asset and its hardest constraint).

11. Sequential I/O and zero-copy as throughput primitives

Shape: move bytes by appending and by kernel page-cache handoff; avoid copies and random access on the hot path.

Seen in: Kafka — transferFrom to sockets, sparse index + ≤4KB scan instead of per-record pointers; LevelDB — LSM writes are sequential by construction, reads amortized by Bloom filters; git — pack files and delta chains trade random access for density on the shipping path.

Why it recurs: hardware grants sequential bandwidth an order of magnitude beyond random; the designs that treat this as physics, not preference, win throughput decades.

Reach for it when: volume is the product. Costs are read amplification and index machinery to find things again.

12. Generate the surface from data

Shape: commands/APIs/config described as data (tables, JSON, schemas) and compiled into dispatch, docs, validation, and clients.

Seen in: Redis — commands.json → table → dispatch/ACL/docs; Kubernetes — OpenAPI schemas → typed clients for unknown future types; CPython — bytecodes.c DSL generating the interpreter and its metadata; FFmpeg — configure generates codec_list.c / filter_list.c from its component lists, so the "plugin registry" is a static C array at link time (print_enabled_components in configure:8774); PyTorch — native_functions.yaml + derivatives.yaml generate the bindings, autograd kernels, backward nodes, and dispatch registrations for 2,000+ operators from one schema pair; Servo — 576 WebIDL files are code-generated into Rust DOM bindings and JS glue, so the web API surface cannot drift from its implementations; linux — syscall_64.tbl is the frozen syscall ABI as one data file, from which the dispatch switch, the __x64_sys_* stubs, and the tracing table are all generated; V8 — the interpreter itself is generated: one IGNITION_HANDLER DSL per bytecode (with Torque-built builtins beside it) compiles to machine-code handlers for every architecture, the same move as CPython's bytecodes.c but stopping at nothing short of code; Chromium — ~1,900 .mojom IDL files compile into typed, versioned IPC bindings for every process boundary, so validation and version skew are build artifacts, not review diligence; Neovim — every nvim_* API function is declared once with FUNC_API attributes in api/*.c; generators emit the perfect-hash dispatch table, Lua bindings, runtime metadata, docs, and the twin server/client halves of the UI event protocol (ui_events.in.h → packers and handlers); LLVM — the pass vocabulary is a macro table (PassRegistry.def) that generates the pipeline parser, and CPU targets are TableGen .td records expanded into generated selector tables (even default<O2> is a registry alias, not driver code — so the optimizer's configuration, its targets, and its extension surface are all data; ClickHouse — settings and factory registrations (engines, functions, codecs, formats) carry their own doc strings, so thousands of knobs and extensions stay user-visible without a second handbook); HotSpot — the interpreter itself is generated at JVM startup from one def() per bytecode (TemplateTable::initialize), emitting a dispatch table of machine code per platform — the same move as CPython's bytecodes.c, one step further down to native code.

Why it recurs: one source of truth removes drift between implementation, documentation, and tooling — the places large systems rot first.

Reach for it when: the surface is large and regular. For small surfaces it is ceremony; past a few dozen operations it is survival.

13. Dumb core, smart edges

Shape: the server/daemon stays a simple mechanism (a hash-map daemon, an append-only log) and pushes sharding, routing, failover, and retry into client libraries that every ecosystem implements independently.

Seen in: Memcached — zero cluster code in the server; consistent hashing (Ketama) and failover live in clients, so the server is just a slab-allocated hash map; Kafka — the broker is a dumb partitioned log; producers and consumer groups own routing, batching, and rebalancing; Redis — the cluster era kept the same split, with MOVED/ASK redirects resolved client-side.

Why it recurs: a dumb core is trivially fast, auditable, and never needs a consensus protocol — provided the data can be rebuilt or reread from somewhere else (a cache's source DB, a log's retention).

Reach for it when: the system's data is derivable and edge-intelligence is deployable (fat clients everywhere). The cost is ecosystem-wide: behavior becomes client-library version skew, and operations that need a global view (rebalancing without client updates, multi-key transactions) become impossible or bolted on later — which is exactly the cliff both Memcached and early Kafka hit, and what ZooKeeper/etcd exist to catch on the coordination side.

14. Speculate, guard, deoptimize

Shape: run a slow-but-correct baseline; record what actually happens (types, shapes, call targets); compile guarded fast paths that assume the observations hold; when a guard fails, fall back to the baseline and record the wider truth. Wrong guesses are a designed control-flow path, not an error.

Seen in: V8 — the full ladder: feedback bytes and IC states observed by Ignition, four tiers of guarded code, Deoptimizer rebuilding interpreter frames, and CompilationDependencies registering invalidations so a Map transition can retire whole batches of optimized code; CPython — the portable middle point: the same feedback-and-guards idea (3.11's adaptive interpreter) specializing bytecode in place, with deopt back to the generic opcode, and no JIT at all. Lua is the control experiment: zero speculation, one honest interpreter.

Why it recurs: dynamic languages hide their types until runtime; when the workload is long-lived, learning-by-running beats both static typing (unshippable) and naive interpretation (unbearably slow). The engineering is not the specialization — it is making retraction complete and cheap, because a guess you cannot safely take back is a crash.

Reach for it when: the hot paths are stable enough to have repeating shapes/types and the process lives long enough to amortize learning. Costs: warmup latency (cold code runs the baseline), memory for feedback and multiple code versions, and deopt storms when shapes churn. Short-lived processes should stay at CPython's specialization tier or Lua's none at all.

15. The intermediate representation is the architecture

Shape: instead of translating problem → solution in one step, the system freezes a serializable intermediate representation at the seam, checks it with a verifier, and makes every transformation a small, composable stage over it — so N producers and M consumers cost N+M, not N×M.

Seen in: LLVM — the pattern's cathedral: a pointer-graph IR with def-use chains, a Verifier enforcing the contract, passes scheduled by a parseable pipeline string, and the whole design cloned again into machine IR; SQLite — every SQL statement compiles to a VDBE bytecode program before it runs, making the query plan inspectable and re-executable; CPython — bytecode as a poor man's IR: no SSA and a stack machine, yet the same bet (serialize the program, then transform it — the adaptive interpreter specializing hot opcodes in place is a mini-optimizer over it); PyTorch — torch.compile captures the eager tape into a graph IR that TorchInductor lowers into Triton/C++ (kernels that bottom out in LLVM — the pattern composing with itself); llama.cpp — ggml tensor graphs: models are dataflow IR that a generic backend executes, which is why 160 architectures are just files.

Why it recurs: the IR is where every concern meets — frontends, optimizers, backends, debuggers, serializers — so freezing it (with a verifier) turns each of those into an independently developed, independently testable program over shared data. V8's tiering (Ignition bytecode → Maglev → TurboFan) is the same insight inside a runtime: each tier is one more lowering over an IR.

Reach for it when: more than one producer or more than one consumer of the program/work exists, or will. The price is paying for the IR itself — a data structure that must stay honest under mutation (LLVM's Use lists, its Verifier, and its serialize-then-parallelize concurrency boundary are the invoice) — and losing whatever your source language knew that the IR doesn't (LLVM's intrinsics list is that loss, itemized).

How to use this index while learning

  1. After finishing any deep-dive, return here and find the patterns it instantiated — the recognition is the lesson compounding.
  2. When designing your own system, scan the "reach for it when" lines: most architecture mistakes visible in review are a pattern applied where its "when" doesn't hold (MVCC without GC, event loop with CPU-heavy handlers, CAS without a retention story).
  3. When two patterns conflict (amortization vs responsiveness, immutability vs latency), the deep-dives' trade-off sections show real systems pricing the conflict — that pricing, not the choice, is the transferable skill.
